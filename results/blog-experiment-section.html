A checkout that takes ~1.5s for one user takes ~3 minutes under 50-user contention. The system doesn't crash — it queues until effectively unavailable (a health check during peak load took 103 seconds to answer).

Act 2 — Profiling contradicted the standard advice

The common wisdom says the database is the bottleneck. Measured: Postgres at ~50% CPU, the single Node.js process at ~150% (event loop saturated). pg_stat_statements later confirmed no slow queries exist — the hottest query averages 2.3ms; Medusa simply issues many small queries per checkout. Indexes were never the answer; the cost lives in the application layer.

[SCREENSHOT 2 HERE] Grafana during single-instance optimized runs — time range 15:40–15:55 IST. Show: Postgres CPU spiking to ~200%+ (bottleneck relocated to DB) and Redis ops/sec now ACTIVE vs flat in Screenshot 1.

Act 3 — Fixes that moved the bottleneck instead of removing it

  • Redis modules + pool 40 (single instance): no throughput gain — the wider pool pushed Postgres to 220% CPU. App-layer cost still dominated.
  • 3 API instances + worker behind containerized nginx: requests failed instantly — Docker Desktop's WSL2 network boundary collapsed under high connection counts, not Medusa. Replaced with a native Node load balancer.
  • 3 instances × pool 40 = 120 connections vs Postgres's default max_connections=100: "FATAL: too many clients already." Scaling out the app multiplied connection demand past the DB ceiling — the textbook reason PgBouncer exists. Fixed with max_connections=300.

Every fix relocated the bottleneck: app CPU → network layer → DB connection limit. Capacity engineering is chasing the bottleneck through every layer, not applying one trick.

Honest ceiling: with the load generator, 4 Node processes, Postgres, Redis and monitoring all sharing one 8-core laptop, ~50–100 concurrent full checkouts is this machine's realistic serving capacity. The optimizations multiplied capacity ~18x at the tier the host can sustain; higher tiers need more hardware, not more configuration.

Act 5 — The oversell test (correctness under stampede)

100 concurrent buyers vs 5 units of stock. Result: stock never went negative (5 stocked / 0 oversold). Under extreme saturation the system failed safe — slow, but never incorrect. Medusa's reservation + workflow compensation held.

Capacity planning: the arithmetic that scales

Black Friday readiness is not one big server. If one properly-configured instance-set sustains X checkouts/sec at acceptable p95, and the event forecast needs Y, deploy ≈ Y/X instance-sets behind load balancers, with a database tier sized for (instances × pool size) connections — via PgBouncer — and Redis shared for events/locks/workflows. The architecture we validated is the miniature of exactly that.

Key lessons

  • Medusa's dev defaults collapse at ~50 concurrent checkouts — production config is not optional.
  • Measure before optimizing: the bottleneck was app CPU, not the database, contradicting the default advice.
  • Scaling out moves bottlenecks downstream: watch the LB layer and DB connection limits (3×40 > 100).
  • Correctness held under all loads tested: zero oversells.
  • Per-instance capacity × fleet size is how real Black Friday planning works; laptop-scale honest numbers beat fabricated big ones.
